## ADDED Requirements

### Requirement: Server-controlled tool context
The system SHALL generate a request ID inside each agent execution and pass it to registered tools through Spring AI `ToolContext`. The request ID MUST NOT be included in the LLM-visible tool schema or generated by the model.

#### Scenario: Request ID reaches a tool
- **WHEN** a tool executes during an agent request
- **THEN** the tool can read the same server-generated request ID from `ToolContext`

#### Scenario: Model cannot control request correlation
- **WHEN** the model receives a registered tool schema and generates tool arguments
- **THEN** no request ID field is exposed for the model to populate or override

### Requirement: Correlated agent observability
The system SHALL log agent-request start, completion, and failure with request ID, duration, and outcome. These logs MUST NOT contain the user message, final response content, credentials, authorization headers, or complete provider configuration.

#### Scenario: Successful agent request is correlated
- **WHEN** an agent request completes successfully
- **THEN** start and completion logs share its request ID and the completion log includes elapsed duration and success status

#### Scenario: Failed agent request is correlated
- **WHEN** an agent request fails
- **THEN** its failure log contains the request ID, elapsed duration, failure status, and server-side diagnostic exception without logging message or response content

### Requirement: Tool execution observability
Every foundation tool execution SHALL record request ID, tool name, start, duration, and success or failure status. A common mechanism MUST NOT indiscriminately log full tool arguments or results.

#### Scenario: Successful tool call is observable
- **WHEN** a registered tool completes successfully
- **THEN** logs identify the request ID and tool name and record its successful status and duration

#### Scenario: Failed tool call is observable
- **WHEN** a registered tool throws an error
- **THEN** logs identify the request ID and tool name and record its failed status, duration, and server-side diagnostic exception

#### Scenario: Sensitive arguments are not logged by default
- **WHEN** the common tool execution mechanism records a call
- **THEN** it does not automatically serialize all input arguments or result fields into logs

### Requirement: Safe tool exception handling
Tool failures SHALL be represented by a common `ToolExecutionException` path, remain contained to the affected request, and be translated at the agent/HTTP boundary to a stable client-safe error. The application process MUST remain available, and the response MUST NOT expose stack traces, tool arguments, provider details, or internal configuration.

#### Scenario: Calculator failure does not crash the service
- **WHEN** a calculator call attempts division by zero during an agent request
- **THEN** the request completes through the configured failure response path and subsequent unrelated requests can still be processed

#### Scenario: Internal failure details are sanitized
- **WHEN** a tool failure reaches the HTTP exception handler
- **THEN** the client receives a stable safe error code and message without the exception stack trace or internal cause text

### Requirement: External-call-free automated verification
The default Maven test lifecycle MUST verify tool behavior, agent service mapping/context construction, controller validation/success behavior, and application wiring without a real model credential or network call.

#### Scenario: Default tests run offline
- **WHEN** `mvn clean test` runs without provider credentials
- **THEN** all agent and tool automated tests use mocked, fake, or scripted model boundaries and make no real provider request

#### Scenario: Tool context is covered automatically
- **WHEN** the agent service test executes through its mocked or scripted AI boundary
- **THEN** it verifies that the server-generated request ID is present in the tool-context configuration

### Requirement: Manual tool-calling verification guide
Operator documentation SHALL provide an opt-in real-model guide for the agent endpoint covering current date, multiplication, system information, multi-step days-until calculation, a no-tool Redis explanation, and a calculator error. The guide SHALL instruct operators to use execution logs, rather than answer content alone, to confirm which tools ran.

#### Scenario: Operator verifies multi-step behavior
- **WHEN** an operator submits a days-until-target-date request with a configured real model
- **THEN** the guide explains how to confirm the model's reasonable tool path, including `getCurrentDate` followed by `calculateDaysBetween` when that path is selected

#### Scenario: Operator verifies no-tool behavior
- **WHEN** an operator submits a general Redis explanation request
- **THEN** the guide explains how to confirm from logs that no foundation tool executed
